## 一、总结

### 我最初的总结

> 1. `get_image_data`：随机取 5 个相机，对图像做缩放、裁剪、翻转、旋转，计算这些操作的仿射变换。
> 2. `get_lidar_data`：扣掉近距离的点，获取近三帧的点云，为了得到更多的点，但要做坐标转换。
> 3. `get_binimg`：将车的标注框拍扁到 BEV 网格中，获取网格坐标，对各个格子填充 1。

### 修正后的总结

1. **`get_image_data`**：读取每个相机的图像和标定参数（`rots`、`trans`、`intrins`）。训练时对每个相机独立做随机缩放、裁剪、翻转、旋转，验证时只做固定的缩放和裁剪。把这些操作累积成一个仿射变换，记为 `post_rot` 和 `post_tran`。
2. **`get_lidar_data`**：在传感器坐标系下删掉近处的无效点和自车点，把当前帧和之前几帧的点云运动补偿到参考关键帧的自车坐标系下，叠加得到更密的点云。只用于 `lidar_check`。
3. **`get_binimg`**：把全局坐标系下的车辆标注框变换到自车坐标系，取底面角点量化到 200×200 网格，框内的格子填 1，生成 BEV 分割标签。

**三个函数的输出都在"当前关键帧时刻的自车坐标系"下**：

- 图像通过 `rots`、`trans` 和这个坐标系关联起来
- 点云通过运动补偿转到这个坐标系
- 标签通过 ego pose 的逆变换转到这个坐标系

所以模型 lift 出来的特征、激光点、标签，才能落在同一张 BEV 网格上互相比较。

### 被纠正的地方

| 我原来的理解 | 实际情况 |

| `get_image_data` 里随机取 5 个相机 | 选相机是 `choose_cams`（`data.py:195`）做的。只有训练时从 6 个里随机取 5 个，验证时 6 个全用，顺序固定 |

| （漏了）`get_image_data` 还读了什么 | 从 `calibrated_sensor` 读出 `rots`、`trans`、`intrins`，这才是 `get_geometry` 最重要的输入 |

## 二、`lidar_check` 是干什么的

**训练前的检查工具**，不涉及网络学习（只调用了 `model.get_geometry`），检查几何和标签有没有静默出错：

| 检查什么 | 图中哪一块 | 出错时的表现 |
|---|---|---|
| 标定参数和增强参数（自车 → 图像） | ① 激光点叠加在相机画面上 | 点和物体对不上 |
| `get_geometry`（图像 → 自车） | ④ 视锥扇形 | 扇形方向或位置不对 |
| 标签栅格化和轴约定 | ② 激光俯视图 vs ③ 标签 | 车的位置对不上，或镜像、转置 |

- 默认用验证集，mini 上会生成 **81 张图**（2 个验证场景：40 + 41 个样本），结果保存在 `lss_viz/lidar_check/`
- 俯视图的方向：**右边是车头方向，上边是车的左侧**
- 相机画面上下方画到图像外面的点不是 bug：验证集裁掉了顶部 48 行、底部 22 行，而画图时判断"在不在图里"用的是原图尺寸 900×1600
- 值得精读的只有 `explore.py:77, 83-85`，加上 `tools.py:80` 的 `ego_to_cam` 和 `:126` 的 `get_only_in_img_mask`。它们正好是 `get_geometry` 的逆过程；画图代码可以跳过
- `get_only_in_img_mask` 里的 `pts[2] > 0` 用来过滤相机背后的点，这是自己写投影代码时最常漏掉的一步

## 三、`get_geometry` 的 5 个入参

分两组：

- **相机标定**：直接从 nuScenes 读出的物理量，同一相机每帧基本一样
- **图像增强**：代码计算得到，每个样本、每个相机都不同

| 参数 | 形状 | 含义 |
|---|---|---|
| `rots` | B×N×3×3 | 相机 → 自车的旋转 R |
| `trans` | B×N×3 | 相机光心在自车坐标系中的位置 t（米） |
| `intrins` | B×N×3×3 | **原图**（1600×900）的内参 K，不随增强改变 |
| `post_rots` | B×N×3×3 | 原图像素 → 增强后像素的线性部分；只有左上 2×2 有内容，深度不变 |
| `post_trans` | B×N×3 | 同一变换的平移部分；第 3 个分量恒为 0 |

**实测值**（验证集，CAM_FRONT）：

- `rots` 的**每一列是相机坐标轴在自车坐标系下的方向**：相机的"右、下、前"分别对应自车的 (0,−1,0)、(0,0,−1)、(1,0,0)
- `trans` = (1.70, 0.02, 1.51)：前方 1.7 米、高 1.5 米。左侧相机 y > 0，右侧相机 y < 0。自车坐标系的原点在后轴中心
- `intrins`：fx = fy = 1266，主点约 (816, 491)
- `post_rot` = diag(0.22, 0.22, 1)，`post_tran` = (0, −48, 0)：缩放 0.22 倍（= 352/1600），裁掉顶部 48 行

**变换链**：

```
get_geometry（图像 → 自车）：
  (u',v',d) → post_rot⁻¹·(· − post_tran) → (u·d, v·d, d) → K⁻¹ → R·p + t

ego_to_cam + explore.py:85（自车 → 图像）：
  p → Rᵀ(p − t) → K· → 前两维除以 z → post_rot·(·) + post_tran → (u',v',d)
```

`rot.permute(1, 0)` 就是 Rᵀ。旋转矩阵是正交矩阵，转置等于逆，不需要调用 `torch.inverse`。

> **面试题**：为什么不把图像增强合并进 K，而要单独维护 `post_rot`、`post_tran`？
> K 保持物理标定值，语义清晰；缩放和裁剪可以合进 K，但翻转和旋转合进去后 K 就不再是标准的上三角形式；拆开后，几何代码只需要统一"先撤销增强，再反投影"。

## 四、`img_transform`：增强能写成一个"旋转 + 平移"吗？

**能，但更准确的说法是一个仿射变换 `p' = A·p + b`。** 其中 A **不是纯旋转矩阵**，而是"缩放 × 翻转 × 旋转"的乘积，`post_rot` 这个名字有误导性。四种操作合起来严格说是 **2D 相似变换**（等比缩放 + 旋转 + 可能的镜像 + 平移）。

| 操作 | A | b |
|---|---|---|
| 缩放 s | `s·I` | 0 |
| 裁剪，左上角 (x₀, y₀) | `I` | `−(x₀, y₀)` |
| 水平翻转，宽 fW | `[[-1,0],[0,1]]` | `(fW, 0)` |
| 绕图像中心 c 旋转 θ | `R_θ` | `c − R_θ·c` |

**仿射变换的复合还是仿射变换**：先做 (A₁, b₁)，再做 (A₂, b₂)，得到 `(A₂A₁, A₂b₁ + b₂)`。代码里每一步都在这样累积：

```python
post_rot  = A.matmul(post_rot)
post_tran = A.matmul(post_tran) + b
```

最终 `A_total = R_θ · F · s`，`det(A_total) = ±s²`，翻转时为负。由于 s > 0，A 一定可逆。

**实测**：在原图上画白点，经过 `img_transform` 后，实际位置与 `A·p + b` 的预测相差 0.5–1.2 px。特征图一格对应输入图上 16 px，所以可以忽略。误差来源：半像素约定、`resize_dims` 取整、PIL 旋转用最近邻插值。

**两个容易混淆的点**：

1. `data.py:151-154` 里的 3×3 `post_rot` **不是齐次矩阵**。它把 A 嵌进左上角、b 单独放在 `post_trans` 里，作用对象是 `(u, v, d)`，深度保持不变。如果是齐次矩阵，b 会放在第三列，作用对象是 `(u, v, 1)`
2. 不是所有增强都能这样表示：**镜头畸变**是非线性的；**模拟相机在 3D 中转动**是单应变换，需要透视除法。后者一般改到外参 `rots` 上

## 五、`get_lidar_data`（`tools.py:23`）

**定位**：略读即可。训练不用它，但它的坐标系变换链是面试常考题，也是后续深度监督、时序融合项目的基础。

### 5.1 `points = np.zeros((5, 0))` 为什么是 (5, 0)

- **5 行**：x、y、z、反射强度（来自 `LidarPointCloud`，`nbr_dims = 4`），再加第 65–68 行补上的 dt
- **0 列**：一开始还没有点。`np.concatenate(..., axis=1)` 要求除第 1 维以外形状一致，`(5, 0)` 和谁拼接都等于对方本身。如果用 `np.zeros(0)` 起步会报 `AxisError`
- **按列存放**（每列一个点）是 devkit 的约定，做变换时可以直接"矩阵 × 点"
- 巧合：原始 `.pcd.bin` 每个点也是 5 个 float，但第 5 维是 ring（线束编号），devkit 读文件时丢掉了它；这里的第 5 维 dt 是函数自己补的
- 在循环里反复 `concatenate` 的复杂度是 O(帧数²)。帧数多时，更好的写法是先 append 到 list，最后统一拼接一次

### 5.2 `remove_close(2.2)`：删掉近处的点

```python
x_filt = np.abs(self.points[0, :]) < radius
y_filt = np.abs(self.points[1, :]) < radius
not_close = np.logical_not(np.logical_and(x_filt, y_filt))
```

- 参数名叫 radius，实际删的是**正方形**（对角方向删到约 3.1 米），而且**不看 z**，是一根上下贯通的柱子
- 在第 48 行执行，坐标变换在第 62 行，所以是在**传感器坐标系**下删的。激光雷达在自车坐标系中位于 (0.94, 0, 1.84)
- 实测每帧删掉约 **27%** 的点，其中约一半离传感器不到 0.3 米（无效回波），其余主要是打在车顶和支架上的点；真正在 1–2.2 米范围内的每帧只有约 660 个

**为什么必须删**：

1. **运动补偿假设点在世界中静止**，而自车点是跟着车动的。实测把 100 ms 前（车速 4.3 m/s）的自车点做补偿后，整体被往后拉了约 0.43 米，叠加多帧会在车后拖出一串假点
2. **必须在变换之前删**：变换后过去帧的自车点已经被搬走，用以车为中心的方框删不干净
3. 代价：紧贴着车的真实物体也会被删掉。更精细的做法是用自车 3D 包围框裁剪，同时单独过滤坐标接近 0 的点

### 5.3 变换链：`car_from_global` 和 `global_from_car` 不是互逆吗？

```python
trans_matrix = reduce(np.dot, [car_from_global, global_from_car, car_from_current])
```

**我的疑问**：这两个矩阵相乘不就是单位矩阵吗？

**答案**：它们用的是**两个不同时刻**的位姿，所以不互逆。

| 矩阵 | 代码位置 | 位姿 |
|---|---|---|
| `car_from_global` | `:39`，在循环**外**算一次 | 参考关键帧时刻的车，固定不变 |
| `global_from_car` | `:51-52`，在循环**内**每轮重算 | 第 i 帧 sweep 时刻的车 |
| `car_from_current` | 每轮重算，但实际结果一样 | 激光外参；mini 每个场景只有 1 条 LIDAR_TOP 标定记录 |

把名字写全会更清楚：`car_ref_from_global · global_from_car_i · car_i_from_lidar_i`。"global" 可以消掉，但 `car_ref ≠ car_i`。乘积是"过去的车相对于现在的车"的相对位姿：

```
T_ref←i = (T_global←ref)⁻¹ · T_global←i
```

**实测**（车速约 4.3 m/s）：

| sweep | 时间 | 平移 (x, y) | 转角 |
|---|---|---|---|
| 0（参考帧本身） | 当前 | (0, 0)，**单位矩阵** | 0° |
| 1 | 50 ms 前 | (−0.21, 0.00) m | −0.64° |
| 2 | 100 ms 前 | (−0.43, 0.01) m | −1.27° |

x 为负，表示过去的车在现在的车后方。之所以要绕道全局坐标系，是因为 `ego_pose` 表只存了每个时刻车相对于全局的位姿，没有存两帧之间的相对位姿。

**我的确认**：循环最后 `current_sd_rec = nusc.get('sample_data', current_sd_rec['prev'])` 往前移一帧，所以 3 帧点云共用同一个 `car_from_global`。✅ 对：**目标坐标系固定，出发坐标系在变**。正因如此，第 69 行才能把各帧点云直接拼在一起；`time_lag` 也是减去固定的 `ref_time`。

### 5.4 为什么要这样做

**为什么叠加多帧**：32 线激光雷达单帧只有约 2.5 万个有效点，远处很稀疏。往前多取 2 帧只回溯 100 ms，点数就变成约 3 倍。

**为什么都变换到当前时刻的车上**：相机参数、标签、BEV 网格都定义在这个坐标系下。如果每帧留在自己的坐标系里，同一面静止的墙会出现 3 次，彼此错开：

- 平移：错开 0.21 米、0.43 米（高速 15 m/s 时是 0.75 米、1.5 米）
- 旋转：离车越远错得越多，40 米外横向偏移约 40 × tan(1.27°) ≈ 0.9 米

**代价**：只补偿了**自车**的运动，其他运动物体会拖影。所以要在帧数上做取舍；CenterPoint 等方法叠 10 帧，并把 dt 作为特征输入网络。这里算了 dt，但 `NuscData.get_lidar_data` 只取了 x、y、z 三行。

### 5.5 源码细节

1. 注释写着 "four matrices"，实际只有 3 个。devkit 原版还有 `ref_from_car`（转到参考激光坐标系），这里删掉了，所以输出在**自车坐标系**。第 35 行的 `ref_cs_rec` 算出来没用，是删掉这个矩阵后的残留
2. **相机和激光不是同一时刻采集的，但 LSS 忽略了这一点**。在 mini 全部 404 个样本 × 6 个相机上实测：时间差中位数 25 ms、最大 48 ms；对应的自车位移中位数 0.08 米、最大 0.65 米（约 1.3 个 BEV 格子）。devkit 的 `map_pointcloud_to_image` 走的是完整链条：激光 → 激光时刻的自车 → 全局 → 相机时刻的自车 → 相机

## 六、`get_binimg`（`data.py:171`）：生成 BEV 车辆标签

| 步骤 | 代码 | 要点 |
|---|---|---|
| ① 参考坐标系 | `:172-175` | 用激光关键帧时刻的 ego pose；`p_ego = R⁻¹(p − t)`，所以 `trans` 取负号、`rot` 取逆 |
| ② 筛选并变换 | `:177-185` | 只保留 `vehicle.*`；**先平移再旋转**，顺序不能换（换了会变成 `R⁻¹p − t`） |
| ③ 量化 | `:187-190` | 取底面 4 个角点的 x、y，高度丢掉；`(p − bx + dx/2)/dx = (p + 50)/0.5`，和 `voxel_pooling` 用同一个网格 |
| ④ 填充 | `:191-192` | `img[ix, iy]`，而 OpenCV 的点是 `(列, 行)`，所以要交换两轴；`fillPoly` 把框内格子填 1 |
| ⑤ 输出 | `:194` | `unsqueeze(0)` → `(1, 200, 200)`，拼成 batch 后与模型输出 `(B, 1, 200, 200)` 对齐 |

### 实测发现

1. **"vehicle" 包括自行车和摩托车**：car 7619、truck 649、motorcycle 471、bus.rigid 353、bicycle 243、construction 196、trailer 60、bus.bendy 57
2. **标签里有大量看不见的车**：可见度 0–40% 的约占 31%，一个激光点都没有的约占 25%。这给 IoU 设了上限。后续一些工作会另外报告"只保留可见度 > 40%"的结果，**不同论文的车辆 IoU 要先看标签设置再比较**
3. **栅格化后的框偏大、偏向一侧**：
   - 合成一辆 4 m × 2 m 的车，理想应占 32 格，实际填了 45 格
   - 真实框的栅格面积是真实面积的 1.38 倍（中位数）
   - 原因：`fillPoly` 会填边界像素、把整数坐标当像素中心，而 `voxel_pooling` 中格子 i 覆盖的是 `[i, i+1)`。结果每个框在 +x、+y 两侧各多一格，整体偏了半格（0.25 米）
   - 训练和评估用同一套标签，所以对本仓库的指标影响不大；和其他实现对比时需要注意
   - 修正思路：判断每个格子中心是否在框内

> **面试题**：BEV 分割的标签是怎么生成的？
> 全局坐标系下的框 → 参考时刻的自车坐标系 → 取底面角点并量化 → 多边形填充。
> 可以补充的讨论点：可见度过滤、像素约定、时间同步。
